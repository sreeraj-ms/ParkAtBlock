Build an ASP.NET Core backend for a real-time smart parking monitoring system.

PROJECT GOAL
---------------
An ESP32 device is connected to an HC-SR04 ultrasonic distance sensor.

The ESP32 monitors a parking slot.

Current logic:
- If distance < 50 cm → vehicle/car is considered PARKED/OCCUPIED.
- If distance >= 50 cm → parking slot is considered AVAILABLE.
- The ESP32 currently has a red LED that turns ON when a vehicle is detected.

The ESP32 will communicate with the ASP.NET Core server over Wi-Fi.

The server must provide:
1. REST API for receiving parking sensor events from ESP32.
2. SignalR for real-time updates to web clients.
3. In-memory storage for current parking state.
4. No SQL Server/database for the first version.
5. Clean architecture so SQL Server can be added later without major changes.

TECHNOLOGY
---------------
- ASP.NET Core Web API
- C#
- .NET 8 or newer LTS version
- SignalR
- REST API
- In-memory state storage
- Swagger/OpenAPI
- Dependency Injection
- Async/await
- Nullable reference types enabled

Do NOT add Entity Framework or SQL Server yet.

CORE DOMAIN
---------------

A parking slot should have:

- SlotId
- DeviceId
- DistanceCm
- IsOccupied
- LastUpdatedUtc
- LastSeenUtc
- DeviceStatus

Example:

{
    "slotId": 1,
    "deviceId": "ESP32-001",
    "distanceCm": 32.5,
    "isOccupied": true,
    "lastUpdatedUtc": "2026-09-03T16:00:00Z",
    "lastSeenUtc": "2026-09-03T16:00:00Z",
    "deviceStatus": "Online"
}

The server should determine IsOccupied based on distance rather than trusting the ESP32's occupied value.

Default threshold:

50 cm

Make the threshold configurable so it can be changed later without changing the API contract.

For example:

ParkingSettings:
- OccupiedDistanceThresholdCm = 50

DEVICE EVENT API
---------------

Create:

POST /api/parking/events

The ESP32 sends:

{
    "deviceId": "ESP32-001",
    "slotId": 1,
    "distanceCm": 32.5
}

The server should:

1. Validate the request.
2. Validate DeviceId.
3. Validate SlotId.
4. Validate distance.
5. Update the current state of that parking slot.
6. Determine IsOccupied using the configured threshold.
7. Update LastUpdatedUtc and LastSeenUtc.
8. Mark the device Online.
9. Broadcast the updated parking slot through SignalR.
10. Return HTTP 200/202 with the updated state.

Do not broadcast an event if the parking state has not changed unless there is a specific reason to do so.

CURRENT STATUS API
---------------

Create:

GET /api/parking/slots

Return all known parking slots.

Example:

[
    {
        "slotId": 1,
        "deviceId": "ESP32-001",
        "distanceCm": 32.5,
        "isOccupied": true,
        "lastUpdatedUtc": "...",
        "lastSeenUtc": "...",
        "deviceStatus": "Online"
    }
]

Also create:

GET /api/parking/slots/{slotId}

Return the current state of one slot.

Return 404 if the slot does not exist.

DEVICE STATUS
---------------

A device should have:

- Online
- Offline

The server should track LastSeenUtc.

Design the code so an ESP32 that stops sending events can eventually be marked Offline.

Do not require a separate heartbeat endpoint initially unless you believe it is necessary.

Provide a clean mechanism/service for determining whether a device is offline.

Create a SignalR hub:

/hubs/parking

ParkingHub : Hub

Use:

IHubContext<ParkingHub>

from the application/service layer rather than putting business logic inside the Hub.

Also provide a mechanism for a newly connected dashboard client to retrieve the current state using the REST API.

Do not over-engineer the project.

The application/service layer should contain the parking business logic.

The controller should remain thin.

BUSINESS RULES
---------------

1. distance < 50 cm → occupied
2. distance >= 50 cm → available

Make 50 cm configurable.

The server should determine occupancy.

Example:

distance = 32
→ IsOccupied = true

distance = 75
→ IsOccupied = false

Avoid unnecessary event broadcasting.

If:

previous state = occupied
new state = occupied

do not send ParkingSlotUpdated unless there is a meaningful state update requirement.

If:

previous state = occupied
new state = available

broadcast ParkingSlotUpdated.

If:

previous state = available
new state = occupied

broadcast ParkingSlotUpdated.

SENSOR NOISE
---------------

Design the service so sensor readings can later support debouncing/hysteresis.

For the first version, keep the logic simple.

However, structure the code so that later we can implement:

- multiple consecutive readings
- configurable occupied threshold
- configurable available threshold
- state stabilization

Do not implement complicated sensor filtering unless necessary for the first version.

CONCURRENCY
---------------

Multiple ESP32 devices may send requests simultaneously.

The in-memory parking state must be thread-safe.

Use appropriate synchronization or a concurrent collection.

Do not use a normal Dictionary without considering concurrent access.

CORS
---------------

Configure CORS so a web dashboard hosted separately can connect to:

- REST API
- SignalR

Do not use unsafe wildcard configuration with AllowCredentials in production.

For development, make the allowed origins configurable through configuration/appsettings.

CONFIGURATION
---------------

Use appsettings.json for:

- AllowedOrigins

Example:

"ParkingSettings": {
    "OccupiedDistanceThresholdCm": 50,

SlotId:
